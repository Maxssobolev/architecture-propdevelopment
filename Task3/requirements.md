# Требования к внешним интеграциям 


## 1) Требования к безопасности

* весь внешний трафик только по **TLS 1.2+**; запрет слабых алгоритмов.
* машинное взаимодействие **Outbound → Partner API** и **Partner Webhook → Inbound** по **mTLS**.
* все входящие в PropDev HTTP-интеграции проходят через **Network Firewall** и **Inbound Webhook Gateway**; прямых вызовов в tenant-core-app нет.
* **OpenAPI/JSON-Schema validation** на входящих/исходящих точках.
* **минимизация данных** — в PropDev не хранить биометрические шаблоны/изображения; только идентификаторы субъектов/устройств, статусы и служебные метаданные.
* явное **согласие** на обработку биометрии/ПДн, цели и сроки хранения, право отзыва; хранение биометрии — у партнёра.
* шифрование **at-rest** в системах PropDev (БД/бэкапы) и у партнёра; ключи — через KMS/Vault, ротация.
* входящие события **Webhook → Inbound** дополнительно подписываются **JWS**.
* секреты и клиентские сертификаты хранить в **Vault/KMS**, с автоматической ротацией (≤ 90 дней) и аудитом.
* аудит всех административных действий (выдача/отзыв доступов, изменения конфигураций).


## 2) Протоколы аутентификации и авторизации

### 2.1. Пользователь ↔ PropDev

* **OIDC Authorization Code + PKCE** (IdP PropDev). Access/ID токены — короткоживущие (≤ 15–30 мин).

### 2.2. PropDev → Партнёр

* **OAuth 2.1 Client Credentials** или **JWT Bearer** + **mTLS**.

### 2.3. Партнёр → PropDev

* **mTLS** + **JWS** подпись тела события.

### 2.4. Автоматическое управление доступами

* Назначение/отзыв разрешений (например, "вход в подъезд", "проезд через шлагбаум") — **через Partner API**:

  * **Scopes**: `access:write`.
  * **Claims**: `subject_id`, `areas[]`, `valid_to`.
  * **Политика**: «наименьшие привилегии», TTL-ограничения, аудит.

## 3) Организация взаимодействия между системами

### 3.1. Потоки

1. **Собственник → Network Firewall → tenant-mobile-api**

   * tenant-mobile-api валидирует сессию (OIDC), применяет RBAC/ABAC по `tenantId/houseId`.
  
2. **tenant-mobile-api → Outbound Integration Client**

   * Внутренний вызов "команда/статус", пробрасывает `trace-id` и контекст тенанта.
  
3. **Outbound → Partner Cloud API**

   * `HTTPS/mTLS` + OAuth2.
   * Команды (например, "открыть домофон/шлагбаум") и запросы статусов.
   * Политики retry/backoff, circuit-breaker, лимиты.
  
4. **Edge-шлюз ↔ Partner Cloud API**

   * Синхронизация телеметрии/событий, с буферизацией при обрывах.
  
5. **Partner Webhook → Inbound Webhook Gateway**

   * События: `INTERCOM.OPENED|DENIED`, `BARRIER.OPENED|DENIED`, др.
   * `mTLS + JWS`, проверка `nonce/timestamp`, идемпотентность; схема — по OpenAPI.
  
6. **Inbound → tenant-core-app**

   * Валидированные события транслируются в бизнес-домен (уведомления, журнал, аналитика).

### 3.2. Надёжность и SLA

* идемпотентные команды, дедупликация событий.
* целевые SLO: **99.9%** доступности для команд

### 3.4. Управление доступами

* централизованный сервис управления доступами в PropDev (UI/админ-API) инициирует разрешения у партнёра.
* аудит создания/изменения/отзыва прав.
